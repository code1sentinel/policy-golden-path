# 0002. OSCAL 1.1.2 is the catalog format and save file

Date: 2026-10-04

## Status

Accepted

## Context

Codify's output has to be something a GRC person can keep, share, and open
again. NIST OSCAL catalogs are the interchange format the product already
targets. The code pins the version:

- `src/codify/project.py` sets `OSCAL_VERSION = "1.1.2"` and writes
  `metadata.oscal-version` on every catalog.
- Tests (`tests/test_project.py`, `tests/test_cli.py`) assert that value.
- CI job `oscal-schema` downloads NIST's
  `oscal_catalog_schema.json` from the `v1.1.2` release and validates
  catalogs produced from Markdown, Word, and a reopened catalog via
  `scripts/validate_oscal.mjs`.

The catalog is also the save file: every clause (with type and reason) lives
in `back-matter`, and each control carries statement, guidance, legacy text,
drafting notes, status, origin, and `derived-from` links. Opening that file
resumes the project. A catalog Codify did not write still opens: each of
its controls becomes a clause to work on.

Codify names its own properties in
`https://grcengineering.club/ns/codify`.

## Decision

- Write and read OSCAL **catalog** JSON, version **1.1.2**.
- Treat the catalog as the project file. Do not introduce a second save
  format.
- Keep CI schema validation on every catalog path we claim to support.
- Any change that emits OSCAL adds or updates a golden-file test and must
  stay schema-valid.

## Consequences

- Bumping OSCAL is a new ADR, a schema-job bump, and a migration story for
  saved catalogs.
- Profiles, SSPs, and other OSCAL models are out of scope until decided.
- Excel, CSV, and the Markdown report are derived views, not the source of
  truth.
